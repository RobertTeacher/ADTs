Paper 4 Student Exam Playbook

Examiner reports are written for teachers. This page translates their recurring observations into practical habits you can use while coding, testing and preparing evidence.

The key mindsetPaper 4 does not only test whether your program runs. It tests whether you implement the exact structure, algorithm, function contract and evidence requested.
What the reports are really telling you:

Many marks are lost by solving a slightly different problem from the one set. Stronger responses tend to read the specification literally, preserve the required algorithm, manage state carefully and test the exact case requested.

A routine to use on every practical task

1Before codingUnderline exact names, parameters, types, pointer meanings, return values and the required algorithm.
2While codingAfter each pointer, index or counter update, check what that variable means now.
3Before evidenceRun the exact test requested and make the result easy for an examiner to read.
SpecificationReport insight

Do not solve the version you remember

Representations and pointer conventions can change between papers.

June 2023 P41/42/43
Exam context

The reports warn that some candidates built a familiar data structure instead of the one specified. Queue questions can also define TailPointer differently.

Why this matters

Your program may look sensible but still be wrong for that question if the representation, initial values or pointer meanings differ.

Student strategy

Before coding, write a tiny contract: structure + pointer meaning + initial values + required return.

Example
TailPointer = next free position NumberItems = number stored Full when NumberItems == len(Queue)

If the paper defines TailPointer differently, change the contract first.

I can explain what every pointer means before I use it.
Linear searchFunction contract

A search does not always return an index

The required result matters as much as the search method.

June 2023 P41/43 Q1
Exam context

Candidates were asked to use linear search to count occurrences. Some returned a matching index instead; others read the target inside the function instead of accepting it as a parameter.

Transferable lesson

“Use linear search” describes the method. The function contract decides whether you return a count, index, Boolean or record.

Student strategy

Write the function header and expected return in plain English before writing the loop.

Quick comparison
first position → return index count occurrences → keep searching, return count exists? → return True / False
My return value answers the exact question asked.
SortingGiven algorithm

Preserve the algorithm Cambridge gives you

Translate it; do not redesign it unless asked.

June 2023 P42 Q1
Exam context

An incomplete sorting algorithm had to be completed and rewritten in the chosen language. Some candidates made large changes that altered its functionality.

Why this matters

A correct final list does not prove you implemented the required algorithm. Marks can depend on its specified structure and operations.

Student strategy

Map pseudocode line by line into Python. Replace pseudocode functions with Python equivalents, but preserve the control flow.

Ask yourself

Am I translating the given algorithm, or replacing it with the algorithm I prefer?

The defining behaviour of the requested sort is still visible.
Circular queuePointer state

A circular queue must actually wrap

Incrementing TailPointer forever creates a linear queue.

June 2023 P42 Q2
Exam context

Weaker solutions incremented TailPointer but never reset it to 0. Others searched for an empty array slot even though NumberItems was supplied to manage the queue.

Transferable lesson

ADT variables are part of the intended model. Use them consistently instead of inventing a different management system.

Student strategy

Test the boundary deliberately: put TailPointer on the final index and mentally run one Enqueue.

Typical wrap
TailPointer = (TailPointer + 1) % len(Queue)
I tested full, empty and wrap-around states separately.
StackAdapt reused code

Copied code still needs a full adaptation check

Similar stacks may have different sizes, files and identifiers.

June 2023 P41 Q3
Exam context

Candidates could reuse one stack pattern for another, but some forgot to change pointer names, capacity, file name, record count or the Push function called.

Why this matters

Reusing a known pattern saves time, but a single old identifier can invalidate otherwise correct logic.

Student strategy

After copying code, scan only for names and constants: array, pointer, size, file, loop count and function call.

No identifier from the previous task remains accidentally.
Return valuesState first

Update state before you return

Nothing after return executes in that call.

June 2023 P42 Q2
Exam context

Some Dequeue solutions returned the record before updating HeadPointer and NumberItems. The first returned value could look correct while the queue state became wrong.

Transferable lesson

An ADT operation has two jobs: produce a result and leave the structure in a valid new state.

Student strategy

Use the order: store result → update structure → return result.

Mental template
item = Queue[HeadPointer] HeadPointer = ... NumberItems -= 1 return item
Nothing important appears after return.
Function callsStore once

Do not call a state-changing function twice

Calling it again can repeat the operation.

June 2023 P42 Q2
Exam context

Some candidates called Enqueue, ignored its return value, then called it again to store the result. The same item was therefore enqueued twice. Similar problems occurred with Dequeue.

Transferable lesson

A function call can modify program state. Repeating the call is not equivalent to reading its previous result.

Student strategy
success = Enqueue(record) if success: ...

Call once, store once, test the returned value.

Each Push, Pop, Enqueue or Dequeue happens exactly as many times as intended.
File handlingComplete workflow

File handling is more than open()

Open, read, convert, close and handle failure coherently.

June 2023 P41/42/43
Exam context

The reports repeatedly mention files being opened but not closed, and exception handling where close() could run even if the file had failed to open.

Transferable lesson

Trace both the success path and failure path. Every statement should make sense in both situations.

Student strategy

Mentally run “file exists” and “file does not exist”. Check where the file object is created and where it is closed.

My file is closed only after it has opened successfully.
EvidenceMake it markable

Correct work still needs clear evidence

The examiner can only mark what is visible and readable.

June 2023 P41/42/43
Exam context

The reports emphasise copying program code into the evidence document as text and using screenshots for output. Tiny, clipped or unreadable output may not demonstrate the required result.

Why this matters

Your evidence document is part of the assessment process, not an afterthought.

Student strategy

Inspect the page like an examiner: can you read the relevant code, see the exact test input and see the complete output?

The exact input and complete output required by the question are visible.
TestingExact case

Finish with the test data Cambridge asked for

Your own test may not expose the behaviour being assessed.

June 2023 P41/43 Q1
Exam context

Some candidates used a different input from the one specified, so their evidence did not show the required result.

Why exact data matters

The selected value may test duplicates, limits, empty/full states or ordering. An easier test can hide a bug.

Student strategy

Use your own tests while developing, but make the final evidence use the exact values requested.

My final evidence uses the specified test data.
